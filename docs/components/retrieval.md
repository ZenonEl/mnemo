# Component: retrieval

**Статус:** 📋 planned. Это «мозг» — то, ради чего остальное собирается.

## Что делает
Семантический поиск + структурные фильтры по всей памяти. Возвращает ответ
**со ссылкой на RAW**. Оформляется как **skill/MCP**, чтобы ассистент запрашивал
память как инструмент.

## Пайплайн
1. **chunk** — нормализованный текст режется на смысловые куски.
2. **embed** — эмбеддинги чанков → векторный индекс; метаданные (дата, проект,
   источник, участник, контур, `raw_path`) → SQLite рядом.
3. **retrieve** — запрос → вектор-поиск (top-k) ∩ структурные фильтры → ранжирование.
4. **answer** — ответ + обязательная ссылка на item/RAW (файл/строка/сообщение).

## Интерфейсы
- **CLI:** `mnemo ask "<вопрос>" [--project X] [--since DATE] [--contour work]`.
- **MCP-сервер:** инструменты `search(query, filters)` и `get(item_id)` поверх
  `retrieve`/RAW. Ассистент дёргает их сам, отвечает с цитатой.
- **skill:** обёртка, чтобы поиск был доступен как навык ассистента.

## Требования
- **Цитируемость обязательна.** Любой ответ ведёт к конкретному RAW. Без
  источника ответ не отдаём.
- **Фильтры не опциональны.** Дата/проект/источник/участник/контур — чтобы не
  мешать рабочее с личным и сужать выдачу.
- **Пересобираемость.** Индекс и эмбеддинги — расходники: удалил → пересобрал
  из RAW. RAW — единственный источник истины.

## Технологический эскиз
- Вектора: на старте sqlite-vec / FAISS локально; вынести при росте.
- Эмбеддинги: через уже используемого провайдера (OpenRouter) или локальная
  модель — в конфиг.
- MCP: отдельный процесс, читает тот же стор.

## Открытые вопросы
- Гибридный поиск (вектор + BM25) — нужен ли сразу.
- Чанкинг: по абзацам / по сообщениям / скользящее окно.
- Реранкер — добавлять ли на старте или после.
- Свежесть: взвешивать ли выдачу по дате.
