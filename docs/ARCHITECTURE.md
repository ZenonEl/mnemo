# ARCHITECTURE — mnemo

_Как оно устроено внутри. Черновик для реализации._

## Общая схема

```
            источники                       ядро (core)                  двери (adapters)
  ┌───────────────────────────┐   ┌──────────────────────────────┐   ┌──────────────────┐
  │ Telegram-переписки        │   │  ingest ──► RAW store         │   │  TG-бот          │
  │ .docx / .xlsx / .md        │──►│    │         (verbatim)      │◄──│  CLI             │
  │ скрины / PNG               │   │    ▼                          │   │  MCP-сервер      │
  │ Claude chat transcripts    │   │  normalize ──► summaries/index│   │  (для ассистента)│
  │ дейлики (GitHub issues)    │   │    │                          │   └──────────────────┘
  └───────────────────────────┘   │    ▼                          │
                                   │  embed ──► vector index       │
                                   │            + metadata (SQLite)│
                                   │  retrieve ◄── query           │
                                   └──────────────────────────────┘
```

## Поток данных (pipeline)

1. **ingest** — коннектор источника кладёт материал в **RAW store** дословно.
   Ничего не переписывает. Присваивает `source_id`, дату, участников, проект.
2. **normalize** — из RAW делает пересказ + запись в индекс (кто/когда/о чём +
   ссылка на RAW). Для docx — извлекает текст и картинки. Идемпотентно:
   повторный прогон обновляет производные, не трогая RAW.
3. **embed** — режет нормализованный текст на чанки, считает эмбеддинги,
   кладёт в векторный индекс; метаданные (дата, проект, источник, путь к RAW) —
   в SQLite рядом.
4. **retrieve** — запрос → семантический поиск + структурные фильтры → ответ
   **со ссылкой на RAW** (файл/строка/сообщение).

## Модель данных

Единица хранения — **item** (сообщение, файл, запись дейлика, реплика чата):

```yaml
item:
  id: <ulid>
  source: telegram | docx | screenshot | claude-chat | daily | ...
  project: <slug|null>          # для фильтра по проекту
  date: YYYY-MM-DD
  participants: [<name>, ...]
  raw_path: raw/<...>           # путь к дословному оригиналу
  summary_ref: summaries/<...>  # где лежит пересказ
  tags: [<tag>, ...]
  contour: work | personal      # разведение контуров, НЕ мешать
```

Файловая раскладка store (по образцу обкатанного chat-export):

```
store/
├── raw/
│   ├── messages/    YYYY-MM-DD_<author>.md
│   ├── attachments/ <оригиналы> + _extracted-text/
│   └── screenshots/
├── summaries/
│   └── <срезы, пересказы>
├── index/
│   ├── INDEX.md            # человекочитаемый
│   └── mnemo.sqlite        # метаданные + вектора (или отдельный vector-store)
```

## Компоненты и границы

| Слой | Ответственность | НЕ отвечает за |
|---|---|---|
| **connectors** | вытащить сырьё из источника → RAW | смысл/поиск |
| **core** | normalize / embed / retrieve | UI/транспорт |
| **adapters** | транспорт (TG/CLI/MCP) | хранение/логику поиска |

Правило: адаптер тонкий, вся логика — в core. Заменить TG на CLI = поменять
дверь, не трогая ядро.

## Технологический эскиз (предварительно, не финал)

- **Язык ядра:** Python (совпадает со стеком рабочих проектов, легко переносить).
- **Метаданные:** SQLite (local-first, ноль инфраструктуры).
- **Вектора:** на старте — sqlite-vec / FAISS локально; при росте — вынести.
- **Эмбеддинги:** через тот же LLM-провайдер, что уже используется (OpenRouter),
  либо локальная модель — вынести в конфиг.
- **MCP:** отдельный сервер поверх `retrieve` (см. `components/retrieval.md`).
- **Шифрование синка:** `age`/`gpg`, в git только зашифрованные бандлы.

## Открытые вопросы (решить при реализации)

- Дедупликация: один и тот же материал из двух источников — как склеивать?
- Инкрементальный ingest: как коннекторы понимают «что нового с прошлого раза»?
- Контуры work/personal: жёсткое разделение стора или один стор + фильтр?
- Ретеншн: чистить ли старые эмбеддинги, если RAW не менялся?
