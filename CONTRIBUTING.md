# Правила работы над mnemo

## Примеры — только обезличенные

**В репозиторий не попадают настоящие имена: проектов, людей, организаций,
логинов, ссылок на внутренние трекеры.** Ни в документации, ни в примерах
команд, ни в комментариях к коду, ни в changelog, ни в сообщениях коммитов.

Правило появилось не из осторожности. В публичной репе успели полежать slug
клиентского проекта, имя и telegram живого заказчика в примерах навыка,
github-логин человека в changelog и полное имя участника в спеке
проектирования. Инструмент, который существует ради того, чтобы клиентские
данные не уезжали наружу, учил этому на настоящих клиентах.

**Находка на живом проекте описывается без опознавательных знаков.** Не
«в `<проект>` нашлось `github: <логин>` у двух записей», а «в рабочем экспорте
один и тот же github-логин нашёлся у двух записей». Ценность находки — в
механике дефекта, и она от обезличивания не теряется.

### Канонические заглушки

Чтобы примеры не расходились между документами, используются одни и те же:

| | Значение |
|---|---|
| slug экспорта | `priyomka`, `sozvony` |
| название | «Приёмка проекта» |
| человек | `Пётр Иванов`, id `petr-ivanov`, telegram `petr_ivanov` |
| внешний трекер | `<репо>#110` |

Идентификаторы записей в примерах — `i004`, `t003`, `q007`, `r001`.

### Локальный список запрещённых слов

`mnemo_selfcheck.py` умеет проверять это механически. Список настоящих имён
лежит **вне репозитория** — иначе он сам был бы утечкой:

```
~/.config/mnemo/private-terms.txt      по слову в строке, # — комментарий
```

Файла нет — проверка молча пропускается, и на посторонних установках ничего не
меняется. Файл есть — любое вхождение в отслеживаемых git файлах становится
расхождением.

Проверка смотрит **рабочее дерево, а не историю**: попавшее в коммит убирается
только переписыванием истории, и лучше не доводить.

## Один текст на оба хоста

mnemo живёт под Claude Code и под Codex **одним комплектом файлов**: всё, что
лежит в `skills/*/SKILL.md`, ставится плагином из маркетплейса в обоих хостах —
`.claude-plugin/` описывает его для Claude Code, `.codex-plugin/` (с
`"skills": "./skills/"`) и `.agents/plugins/marketplace.json` для Codex. Навыки в
обоих хостах зовутся одинаково: `mnemo:chat-export`, `mnemo:work-state`. Второй
копии инструкции не заводится — разошедшиеся копии учат двум разным стандартам,
а расхождение замечают позже, чем оно появилось.

**Новый навык не требует регистрации**, но требует своего `agents/openai.yaml`
рядом с `SKILL.md` — это метаданные для Codex. Самопроверка сверяет и наличие
файла, и совпадение имени навыка с именем каталога.

Отсюда следствия:

- **Различаться может адрес, но не смысл.** Файл инструкций хост-проекта
  называется `CLAUDE.md` или `AGENTS.md` — блок, который туда дописывается,
  побайтно один и тот же. Это закреплено тестом.
- **Путь до скриптов считается от `SKILL.md`, а не от текущего каталога** и с
  разрешением символических ссылок: под Codex скил подключён ссылкой, и наивный
  `../..` уводит в каталог ссылок.
- **Инструкция не обещает того, чего не проверяли запуском.** Способ установки
  под каждый хост прогоняется целиком, а не пишется по образцу другого
  инструмента.

## Маршрутизация проверяется прогоном, а не спором

Навыков два, и поднимает их модель сама — по тому, о чём идёт разговор. Проверить
это чтением нельзя: первый же спорный случай решался бы в спорах. Штатный прогон —
`claude plugin eval`, кейсы лежат в `evals/`:

```
claude plugin eval .                          # весь набор
claude plugin eval . --case "*routes*"        # только маршрутизация
claude plugin eval . --ablation with-without  # плечо без плагина
```

Форма кейса — `prompt.md` с фронтматтером плюс `graders/*.md`. Что меряется:

| Кейс | Что проверяет |
|---|---|
| `blocker-phrase-routes-to-work-state` | «я упёрся» поднимает `work-state` и требует предъявить попытку |
| `status-question-routes-to-work-state` | «всё сделали по ТЗ?» поднимает `work-state`; на пустом реестре — честное «сверять не с чем» |
| `material-still-routes-to-chat-export` | приём материала не деградировал и не перетянут вторым навыком |
| `question-gate-thins-the-list` | заслон на вопрос даёт ожидаемый расклад на разобранном случае |

Плечо `--ablation with-without` показывает, что без плагина нужный навык не
поднимается вовсе, — иначе кейс подтверждает не плагин, а общую сообразительность
модели. В этом режиме грейдеры `tool_used: Skill` объявлены **индикатором**
срабатывания плагина, а не частью счёта: в плече без плагина они не сработают
никогда, и сравнивать по ним нечего. Поэтому **у каждого кейса обязан быть хотя
бы один грейдер про поведение**, а не только про поднятие навыка. Кейс с одними
`Skill`-грейдерами в режиме сравнения оценивать нечем.

**Что этим НЕ измеряется — прямо.**

- Прогон видит только сторону Claude Code. Под Codex список навыков, который
  видит модель, печатает `codex debug prompt-input` — там обязаны быть обе
  строки, `mnemo:chat-export` и `mnemo:work-state`. Читает он **установленную**
  копию плагина, а не рабочее дерево: пока новая версия не установлена, второй
  навык там не появится, и это не дефект.
- `claude plugin eval` на момент написания в раннем доступе и включён не у всех:
  на выключенном аккаунте он отвечает «currently in early access» и код `1`.
  Кейсы при этом лежат в репозитории и ничем не проверены. Дописывая кейс, не
  считай его пройденным, пока не увидел вывод прогона.

Грейдер типа `llm` судит по смыслу и шумит; на нём держатся только те критерии,
которые детерминированно не выражаются. Всё, что можно проверить запуском,
проверяется в `tests/`, а не здесь.

## Остальное

- **`SPEC/STANDARD.md` — источник истины.** Расхождение поведения инструмента со
  стандартом — дефект инструмента, а не повод переписать стандарт.
- **После любой правки:** `python3 scripts/mnemo_selfcheck.py`, затем
  `python3 -m unittest discover -s tests`, затем линтер по рабочим экспортам.
- **Новая гарантия не считается закрытой, пока мутация не покрасила тест.**
  Сними защиту, убедись, что тест падает, восстанови. Зелёный тест при снятой
  защите означает, что он держит не то, что ты думаешь.

  **И саму мутацию проверяй.** «Мутация выжила» читается как «тест слабый», а
  чаще означает «правка не восстановила дефект»: за один день это случилось
  трижды у трёх разных исполнителей — снялась часть записей, правилась строка с
  комментарием вместо кода, соседняя проверка всё равно ловила случай.
  Надёжнее подставить дословно тот код, что стоял до починки, чем сочинять
  поломку заново.
- **Тесты — на стандартной библиотеке** (`unittest`), как и всё остальное:
  ставить ради них pytest значит нарушить обещание «ничего не надо ставить».
  Туда идёт поведение команд, которого не видят ни линтер, ни самопроверка.
- **Версия стандарта поднимается в `STANDARD.md` и в `SPEC_VERSION`** — иначе
  самопроверка не пропустит.
- **Версия плагина поднимается сразу в трёх манифестах** — `.claude-plugin/plugin.json`,
  `.claude-plugin/marketplace.json`, `.codex-plugin/plugin.json` — при каждой
  правке, которая должна доехать до установленных копий: обновление в обоих
  хостах сверяет только её и при совпадении не копирует ничего, рапортуя, что
  всё уже свежее. Расхождение ловит самопроверка.
- **Публичные версии следуют SemVer.** Каждый выпуск получает подписанный тег
  `vX.Y.Z`, GitHub Release и запись в корневом `CHANGELOG.md`; тег обязан
  совпадать с версиями в `plugin.json` и `marketplace.json`.
- **Скрипты — только стандартная библиотека Python 3.** Зависимость превращает
  «ничего не надо ставить» в неправду.
- **Каждая команда в документации прогоняется**, а не пишется по памяти. Так
  нашлось, что `redact` требует `--scope`.
